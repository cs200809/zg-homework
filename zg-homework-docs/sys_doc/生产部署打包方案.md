# 生产部署打包方案（多项目共存版）

本文是 **zg-homework 服务端 + 前端** 在生产机上的权威部署文档。生产机上**多个项目共存**，本项目按
**同域名 + 路径前缀**的方式接入共享 nginx。

本文所写的**每一个端口、路径、参数名、默认值、退出码**都与仓库内脚本的真实行为逐字一致。脚本是权威，
本文只是把脚本的行为整理成运维可以照着执行的步骤。

相关文档：

- 设计与取舍：`zg-homework-docs/superpowers/specs/2026-11-13-multi-project-deploy-design.md`
- 运行环境配置：`zg-homework-docs/sys_doc/config.md`

## 零、阅读约定

### 0.1 占位符声明（执行前必须替换）

本文里所有形如下列的值都是**占位符**，是给人看的示例，**不是可以直接粘贴执行的内容**。
执行前必须替换成生产环境的真实值：

| 占位符 | 出现位置 | 替换成 |
|---|---|---|
| `xxx.com` | §6.2、§8、§11.1 | 生产站点域名 |
| `密码` | 各处 `--database-url` 里的数据库口令 | 真实的数据库口令 |
| `zg_hw_user` / `homework_points` | 各处 `--database-url` | 真实的数据库用户名 / 库名 |
| `prod` | 各处 `scp` / `ssh` | 真实的 ssh 主机别名（或 `user@host`） |
| `<hash>.js` | §11.1 静态资源验证 | 构建产物里真实的带哈希文件名 |
| `<上一版时间戳>` | §10 回滚预案 | 上一版静态包名里的真实时间戳 |

> `--database-url` 里的口令若含 `'`、`"`、`\`、`$` 或首尾空白，会被 env 校验直接拒绝（§4.3）。
> 最省事的做法是**先在 `/etc/zg-homework-server/env` 里写好 `DATABASE_URL`**，让 `install.sh`
> 以已有文件为基底保留它（§4.3），命令行上就不再传 `--database-url`。

`$TS`、`$SERVER_PKG`、`$WEB_SRC_PKG`、`$WEB_PKG` 是**变量**，由 §0.2 / §10 的命令现场赋值，不需要手改。
`$WEB_PKG_PREV`（上一版静态包）需要按实际文件名替换，见 §9.2。

### 0.2 包名与时间戳约定

全文统一使用「模块名 + 形态 + 时间戳」：

```bash
TS=$(date +%Y%m%d-%H%M%S)
SERVER_PKG=/tmp/zg-homework-server-$TS.tar.gz
WEB_SRC_PKG=/tmp/zg-homework-web-source-$TS.tar.gz
WEB_PKG=/tmp/zg-homework-web-static-$TS.tar.gz
```

- 时间戳格式固定 `%Y%m%d-%H%M%S`；
- 服务端部署包：`zg-homework-server-<TS>.tar.gz`；
- 前端**源码包**：`zg-homework-web-source-<TS>.tar.gz`（把部署脚本送到生产机用，见 §5.2）；
- 前端**静态包**：`zg-homework-web-static-<TS>.tar.gz`（发布用）。

## 一、多项目共存拓扑

### 1.1 拓扑

```
生产机 :80/:443
└── 共享 nginx（主配置、server 块、TLS 证书 = 运维统一维护，本项目一律不碰）
    ├── /other/…        → 其它项目（各自的片段）
    ├── /homework/      → 本项目前端静态资源
    │     alias /var/lib/zg-homework-web/current/
    └── /homework_api/  → 本项目后端接口
          proxy_pass http://127.0.0.1:8000
          └── systemd: zg-homework-server.service
               └── /data/apps/zg-homework-server   （代码检出，WorkingDirectory）
```

同域名下多个项目只能靠**路径前缀**区分，因此路径前缀就是每个项目的身份标识。前缀在 nginx 的
`location` 层匹配，**不经过**后端；后端路由自带 `/homework_api` 前缀（`zg-homework-server/app/main.py:45`），
由 `proxy_pass` 原样透传。

### 1.2 资源归属清单

| 资源 | 归属 | 说明 |
|---|---|---|
| 路径前缀 `/homework/`、`/homework_api/` | 本项目 | 多项目共存下的唯一身份标识 |
| 端口 `127.0.0.1:8000` | 本项目 | 只能监听回环地址，不对外暴露 |
| `/data/apps/zg-homework-server/` | 本项目 | 服务端代码检出；systemd `WorkingDirectory` 必须逐字等于它 |
| `/data/apps/zg-homework-server/.venv/` | 本项目 | Python 虚拟环境；由 `init_check.sh` 创建，**不覆盖已有** |
| `/data/apps/zg-homework-web/` | 本项目 | 前端**源码**检出（含 `scripts/install.sh`、`scripts/web_deploy.sh`）；由前端源码包解包落地，见 §5.1 |
| `/var/lib/zg-homework/` | 本项目 | 上传数据根目录（`uploads/`、`private_homework/`） |
| `/var/lib/zg-homework-web/` | 本项目 | 前端发布根目录（`releases/`、`current` 符号链接） |
| `/etc/zg-homework-server/env` | 本项目 | **唯一**的生产配置文件 |
| `/etc/systemd/system/zg-homework-server.service` | 本项目 | systemd 单元 |
| `/etc/nginx/conf.d/zg-homework.conf` | 本项目 | 共享 nginx 中**本项目自己的片段** |
| 共享 nginx 的主配置、站点配置目录 | **运维** | 本项目脚本一律不写 |
| server 块、TLS 证书 | **运维** | 同域名共用一张证书，本项目不申请、不续期 |

### 1.3 写入纪律（硬边界）

1. 本项目任何脚本**不得**写共享 nginx 的主配置，也**不得**写发行版默认布局中的站点配置目录
   （主配置下用于放置站点配置的 `sites-*` 目录）。这两处由运维统一维护。
2. 本项目只允许写自己的 `/etc/nginx/conf.d/zg-homework.conf` 与 `/var/lib/zg-homework-web/`。
3. 本项目片段内**只允许 `location` 块**，不得出现 `server` / `events` / `http` 块——否则会与运维维护的
   server 块冲突或重复监听。
4. **reload 共享 nginx 是本项目对其它项目的唯一跨项目影响面**，因此脚本一律先 `nginx -t` 通过才 reload。
   nginx 的 reload 是平滑的：老 worker 处理完在途连接后退出，不打断其它项目的请求。

脚本层面已经把这几条纪律固化为硬校验，**不依赖人工自律**：

- 服务端 `install.sh` 的 `--env-file` 只接受默认值 `/etc/zg-homework-server/env`；
- 前端 `install.sh` 的 `--snippet-file` 只接受默认值 `/etc/nginx/conf.d/zg-homework.conf`，
  `--deploy-dir` 只接受默认值 `/var/lib/zg-homework-web`；
- 前端 `web_deploy.sh` 的 `--deploy-dir` 同样只接受默认值 `/var/lib/zg-homework-web`；
- 前端 `install.sh` **只写自己的那一个片段** `/etc/nginx/conf.d/zg-homework.conf`（这就是它的全部职责）；
  `web_deploy.sh` **不写** `/etc/nginx/` 下的任何文件（它只做 `nginx -t` 校验与 reload）；
- 共享 nginx 的**主配置**、`server` 块与 **TLS 证书**，本项目**任何脚本都不写**（见 §6.2）。

## 二、路径前缀与端口分配

### 2.1 本项目的固定分配

| 项 | 值 | 由谁决定 |
|---|---|---|
| 前端路径前缀 | `/homework/` | 前端 `install.sh --web-prefix`（默认） |
| 后端路径前缀 | `/homework_api/` | 前端 `install.sh --api-prefix`（默认）；与后端 `app/main.py` 的 `API_PREFIX` 一致 |
| 后端监听地址 | `127.0.0.1:8000` | 服务端 `install.sh --api-port`（默认）、`server_run.sh` 的 `SERVER_PORT`（默认） |
| nginx 上游 | `127.0.0.1:8000` | 前端 `install.sh --api-upstream`（默认，只允许 `127.0.0.1`） |

两个前缀都必须**以 `/` 开头并以 `/` 结尾**，否则前端的 `install.sh` 会拒绝执行。
`/homework_api/` 不会被 `/homework/` 抢匹配——后者要求前缀以斜杠结尾。

### 2.2 新增项目时的约定

1. **前缀登记**：在服务器上维护一张「项目 → 前缀 / 端口 / 片段路径 / 发布目录 / 数据库名」的表。
   新项目的两个前缀不得与已有项目的任何前缀重叠，也不得互为前缀（如 `home` 与 `homework`）。
2. **端口分配**：每个后端项目独占一个回环端口，发布前先查占用：

   ```bash
   ss -ltnp | grep ':8000' || echo '8000 空闲'
   ```

3. **端口改动必须三处同步**（服务端 `install.sh` 会主动提示）：

   ```bash
   # 1) 服务端单元与健康检查端口
   sudo sh zg-homework-server/scripts/install.sh \
     --server-dir /data/apps/zg-homework-server \
     --api-port 8080 \
     --database-url 'mysql+pymysql://zg_hw_user:密码@127.0.0.1:3306/homework_points?charset=utf8mb4' \
     --data-dir /var/lib/zg-homework

   # 2) server_run.sh 校验单元时按 SERVER_PORT 解析 ExecStart，必须一并指定
   #    注意写成 sudo SERVER_PORT=8080 sh ...：把变量赋值放在 sudo 之后，
   #    不依赖 sudo 是否透传命令行上的 VAR=value
   sudo SERVER_PORT=8080 sh zg-homework-server/scripts/server_run.sh check

   # 3) nginx 片段的上游
   sudo sh zg-homework-web/scripts/install.sh --api-upstream 127.0.0.1:8080
   ```

   端口不是 8000 时，`install.sh` 结束会打印提醒：
   `注意：端口不是 8000，请以 SERVER_PORT=<port> 执行 sh scripts/server_run.sh，否则它会拒绝本次安装的单元`。
4. **每项目一个片段文件**：`/etc/nginx/conf.d/<项目名>.conf`，内容只有 `location` 块。
5. **每项目一个发布目录**：`/var/lib/<项目名>-web/`，与片段里的 `alias` 指向同一处。

## 三、目录与数据规划

| 路径 | 内容 | 生命周期 / 权限 |
|---|---|---|
| `/data/apps/zg-homework-server/` | 服务端代码检出 | 升级时覆盖；`.venv` 在其内部 |
| `/data/apps/zg-homework-server/.venv/` | Python 虚拟环境 | `init_check.sh` 创建，**已存在则复用不覆盖** |
| `/data/apps/zg-homework-web/` | 前端源码检出（`src/` + `scripts/`） | 由前端**源码包**解包落地；升级时覆盖 |
| `/data/apps/zg-homework-web/scripts/` | 前端部署脚本 | `install.sh`、`web_deploy.sh` 等；源码包的主要用途就是把它们送到主机（见 §5.2） |
| `/var/lib/zg-homework/uploads/` | 公开上传文件 | 持久；`0750`，属主 `www-data:www-data` |
| `/var/lib/zg-homework/private_homework/` | 私有作业附件 | 持久；`0750`，属主 `www-data:www-data` |
| `/var/lib/zg-homework-web/releases/<版本>/` | 前端发布产物 | 每次发布新增一个目录，**不自动删除** |
| `/var/lib/zg-homework-web/current` | 指向当前版本的符号链接 | 原子切换，切换后 reload 失败会自动回滚 |
| `/etc/zg-homework-server/env` | 服务端生产配置 | `0640`，属主 `root:www-data`；**唯一** |
| `/etc/systemd/system/zg-homework-server.service` | systemd 单元 | `0644` |
| `/etc/nginx/conf.d/zg-homework.conf` | 共享 nginx 片段 | `0644` |

### 3.1 上传数据为什么必须外置

上传数据**必须**放在代码检出目录之外，而且规则比「检出目录之外」更严：

> `UPLOAD_DIR` 与 `PRIVATE_HOMEWORK_DIR` 不得等于、也不得位于**服务端检出目录的上级目录**之下。

这是 `server_run.sh` 的强校验（以检出目录的**父目录**为基准判定），服务端 `install.sh` 用同一条规则做前置
校验。默认布局下检出目录是 `/data/apps/zg-homework-server`，其父目录是 `/data/apps`，
所以 `/var/lib/zg-homework/` 天然满足。

两条理由：

1. **升级会覆盖代码目录**。服务端升级的方式是覆盖 `/data/apps/zg-homework-server/`，若上传文件放在里面，
   就会被覆盖丢失。
2. **校验会直接拒绝**。落在检出目录（或其父目录）下的上传路径，`server_run.sh check` 报
   `UPLOAD_DIR 必须为检出目录之外、不重叠的绝对路径`，服务根本起不来。

此外两个目录**不得互相重叠**（`uploads` 不能是 `private_homework` 的父目录或子目录）。

## 四、服务端部署

### 4.1 一键安装

前置：代码已部署到 `/data/apps/zg-homework-server`，MySQL 库已建好，`.venv` 未创建。

```bash
cd /data/apps/zg-homework-server

sudo sh scripts/install.sh \
  --server-dir /data/apps/zg-homework-server \
  --api-port 8000 \
  --service-user www-data \
  --service-group www-data \
  --database-url 'mysql+pymysql://zg_hw_user:密码@127.0.0.1:3306/homework_points?charset=utf8mb4' \
  --data-dir /var/lib/zg-homework
```

同域名反代部署下 `CORS_ORIGINS` 通常留空——**不传该参数**即可：不传时若已有配置则保留原值，
若仍是模板占位符则置空。

脚本会依次完成：校验 → 建 `.venv`（复用 `scripts/init_check.sh`）→ 建数据目录 → 写 env → 渲染并写 systemd
单元 → `systemctl daemon-reload` → `systemctl enable --now zg-homework-server`。

### 4.2 参数表（与服务端 `install.sh --help` 逐字一致）

| 参数 | 默认值 | 说明 |
|---|---|---|
| `--server-dir` | `/data/apps/zg-homework-server` | 服务端代码检出目录，必须包含 `app/main.py` |
| `--api-port` | `8000` | 后端监听端口（仅 `127.0.0.1`）；会规范化为 `str(int(port))` |
| `--service-user` | `www-data` | systemd 运行用户 |
| `--service-group` | `www-data` | systemd 运行组 |
| `--env-owner` | `root:<service-group>` | env 文件属主 `user:group`；非 root 属主会告警 |
| `--database-url` | **必填** | 必须以 `mysql+pymysql://` 开头、以 `charset=utf8mb4` 结尾 |
| `--jwt-secret` | 无 | 不给则随机生成 32 字节 hex（优先 `openssl rand -hex 32`）；**密钥不打印到终端** |
| `--cors-origins` | 无 | 逗号分隔的来源列表；同域反代通常留空；不给则保留已有配置 |
| `--data-dir` | `/var/lib/zg-homework` | 上传数据根目录；必须在检出目录的**父目录**之外 |
| `--env-file` | `/etc/zg-homework-server/env` | **只接受该默认值**；改成别的路径会让 `server_run.sh` 拒绝该单元 |
| `--unit-file` | `/etc/systemd/system/zg-homework-server.service` | systemd 单元路径；非默认值只告警 |
| `--root` | `/` | 根前缀，仅用于沙箱测试 |
| `--skip-venv` | 关 | 跳过虚拟环境创建 |
| `--no-start` | 关 | 安装后不启动服务 |
| `--force-env` | 关 | 丢弃已有生产配置并整体重建 |

**退出码**：`0` 成功；`2` 参数错误（缺 `--database-url`、无法识别的参数等）；`1` 其它校验/IO 失败。

### 4.3 env 文件的生成语义（重要）

`/etc/zg-homework-server/env` 是**唯一**的生产配置文件，权限 `0640`、属主 `root:www-data`。
`install.sh` 重复执行时**以已有文件为基底**：

- `DATABASE_URL`、`UPLOAD_DIR`、`PRIVATE_HOMEWORK_DIR` 每次按本次参数写入；
- `JWT_SECRET` **只有显式传 `--jwt-secret` 才覆盖**，否则保留已有值——避免轮换密钥导致已签发的
  token 全部失效；`CORS_ORIGINS` 同理，不传则保留；
- 运维**手工添加的键**（例如 `ADMIN_INIT_PASSWORD`）一律保留，不会被模板清空；
- 模板 `production.env.example` 只负责补齐文件里**缺失**的键；
- 原值仍是 `__REPLACE_ME__` 占位符时会被替换（`JWT_SECRET` 换成新生成的密钥，`CORS_ORIGINS` 置空），
  占位符绝不会漏进产物；
- 重复键只保留最后一次出现，避免 `server_run.sh` 拒绝整个文件。

只有传 `--force-env` 才会丢弃已有文件整体重建——**这会让 `JWT_SECRET` 重新生成并使存量 token 失效**，
生产环境慎用。

值的硬约束是**两条规则，适用范围不同**，不要混为一谈：

- **字符规则适用于文件里的每一个键**：取值含 `'`、`"`、`\`、`$`、控制字符（ASCII < 32 或 127），
  或有首尾空白，该行直接被拒绝；
- **占位符规则只适用于五个键**：`DATABASE_URL`、`JWT_SECRET`、`UPLOAD_DIR`、`PRIVATE_HOMEWORK_DIR`、
  `CORS_ORIGINS` 的取值若仍含 `__…__` 占位符会被拒绝；其余键不参与这项检查。

允许的键集合固定为：`APP_NAME`、`ENV`、`DEBUG`、`DATABASE_URL`、`DB_ECHO`、`JWT_SECRET`、
`JWT_ALGORITHM`、`JWT_EXPIRE_DAYS`、`ADMIN_INIT_PASSWORD`、`CORS_ORIGINS`、`UPLOAD_DIR`、
`PRIVATE_HOMEWORK_DIR`、`MAX_UPLOAD_MB`、`ALLOWED_EXTENSIONS`、`ARTICLE_ALLOWED_EXTENSIONS`、
`ARTICLE_MAX_UPLOAD_MB`、`REGISTER_RATE_LIMIT`、`ACTION_RATE_LIMIT`。
写进文件里的多余键会让 `server_run.sh` 直接拒绝该文件。

### 4.4 等价手工步骤

`install.sh` 做的事可以手工复现，步骤如下：

```bash
# 1) 建虚拟环境（脚本：init_check.sh；已存在会拒绝覆盖，需先自行删除旧的 .venv）
cd /data/apps/zg-homework-server
INIT_PYTHON=python3.12 sh scripts/init_check.sh

# 2) 建数据目录
sudo mkdir -p /var/lib/zg-homework/uploads /var/lib/zg-homework/private_homework
sudo chmod 750 /var/lib/zg-homework/uploads /var/lib/zg-homework/private_homework
sudo chown -R www-data:www-data /var/lib/zg-homework

# 3) 生成生产配置（唯一路径，权限 0640）
sudo mkdir -p /etc/zg-homework-server
sudo tee /etc/zg-homework-server/env > /dev/null <<'EOF'
ENV=prod
DEBUG=false
DATABASE_URL=mysql+pymysql://zg_hw_user:密码@127.0.0.1:3306/homework_points?charset=utf8mb4
DB_ECHO=false
JWT_SECRET=__REPLACE_ME__
JWT_ALGORITHM=HS256
JWT_EXPIRE_DAYS=7
ADMIN_INIT_PASSWORD=
CORS_ORIGINS=
UPLOAD_DIR=/var/lib/zg-homework/uploads
PRIVATE_HOMEWORK_DIR=/var/lib/zg-homework/private_homework
MAX_UPLOAD_MB=10
ALLOWED_EXTENSIONS=jpg,jpeg,png,pdf
ARTICLE_ALLOWED_EXTENSIONS=pdf,docx
ARTICLE_MAX_UPLOAD_MB=10
REGISTER_RATE_LIMIT=10
ACTION_RATE_LIMIT=10
EOF
# 生成随机密钥并替换占位符（值不得带引号/反斜杠/首尾空白）
sudo sed -i "s|^JWT_SECRET=__REPLACE_ME__$|JWT_SECRET=$(openssl rand -hex 32)|" \
        /etc/zg-homework-server/env
sudo chmod 640 /etc/zg-homework-server/env
sudo chown root:www-data /etc/zg-homework-server/env

# 4) 渲染 systemd 单元（模板：scripts/zg-homework-server.service.example）
#    替换 __SERVER_MODULE_DIR__ / __SERVER_PYTHON__ / __SERVICE_USER__ /
#    __SERVICE_GROUP__ / __SERVER_PORT__ 五个占位符
sudo sed -e 's#__SERVER_MODULE_DIR__#/data/apps/zg-homework-server#g' \
         -e 's#__SERVER_PYTHON__#/data/apps/zg-homework-server/.venv/bin/python#g' \
         -e 's#__SERVICE_USER__#www-data#g' \
         -e 's#__SERVICE_GROUP__#www-data#g' \
         -e 's#__SERVER_PORT__#8000#g' \
        /data/apps/zg-homework-server/scripts/zg-homework-server.service.example \
        | sudo tee /etc/systemd/system/zg-homework-server.service > /dev/null
sudo chmod 644 /etc/systemd/system/zg-homework-server.service

# 5) 载入并启动
sudo systemctl daemon-reload
sudo systemctl enable --now zg-homework-server
```

单元模板里的 `ExecStart` 必须**逐字**等于：

```
<server-dir>/.venv/bin/python -m uvicorn app.main:app --host 127.0.0.1 --port 8000 --workers 1
```

`--workers 1` 是硬要求，见 §11.3。`EnvironmentFile` 必须是 `/etc/zg-homework-server/env`（唯一环境文件），
`Type=simple`，`KillMode=control-group`，`Environment=` 只有 `PYTHONDONTWRITEBYTECODE=1` 与
`ZG_HOMEWORK_SYSTEMD_PRODUCTION=1` —— 多写一条 `server_run.sh` 就会拒绝控制这个单元。

### 4.5 `server_run.sh` 的用法

```bash
cd /data/apps/zg-homework-server

sudo sh scripts/server_run.sh check      # 全量契约校验（配置、单元、进程归属、端口、健康检查）
sudo sh scripts/server_run.sh status     # 只看状态
sudo sh scripts/server_run.sh start      # 幂等：已运行且健康则不动
sudo sh scripts/server_run.sh stop
sudo sh scripts/server_run.sh restart    # 升级后使用
```

可用环境变量：`SERVER_UNIT`（默认 `zg-homework-server.service`）、`SERVER_PORT`（默认 `8000`）、
`SERVER_PYTHON`（默认 `<检出目录>/.venv/bin/python`）。端口不是 8000 时必须带 `SERVER_PORT=<port>`。

`check` 会验证：单元已加载且无需 `daemon-reload`；`WorkingDirectory` 等于检出目录；`Type`/`KillMode` 符合约定；
没有多余钩子；环境文件唯一且路径正确；管理器环境里没有应用/Python/Uvicorn 相关变量；
`ExecStart` 与约定逐字一致；运行中的主进程命令行、工作目录、cgroup、环境变量都与单元吻合；
**端口由该单元独占**；配置文件格式受支持；`app/` 目录里没有符号链接和字节码残留。
健康检查走的是 **`POST` `/homework_api/health`**。

`check` 失败时不会修改任何东西；`status` 与 `check` 是只读的。

### 4.6 打包与上传（`server_package.sh`）

```bash
cd <开发机上的 zg-homework-server 检出目录>
sh scripts/server_package.sh
# 默认输出：<仓库根>/zg-homework-tests/tar/zg-homework-server-<时间戳>.tar.gz
# 指定输出（必须是两个模块目录之外的新 .tar.gz 文件）：
sh scripts/server_package.sh -o "$SERVER_PKG"
```

包内的内容分两类：

- **目录树**：`app/`（含 `seed/`、`utils/`、`routers/` 等）——遍历时过滤掉隐藏文件、`__pycache__`、
  虚拟环境、上传数据与缓存；
- **白名单里逐个固定的文件**：`requirements.txt`、**`.env.example`**、**`Dockerfile`**、
  **`.dockerignore`**、**`README.md`**，以及 `scripts/` 下的 `install.sh`、`server_run.sh`、
  `server_package.sh`、`init_check.sh`、`production.env.example`、`zg-homework-server.service.example`。
  这一组是**逐个指名加入**的，**绕过了隐藏文件过滤**——所以 `.env.example` / `.dockerignore` 确实在包里。

> `.env.example` 里是**样例值**（示例数据库口令 `root:12345678`、示例 `JWT_SECRET`），
> **不含任何生产凭据**；但它也不是可以直接用的配置——落到服务器后必须替换成真实值，
> 或直接以 `/etc/zg-homework-server/env` 为准（§4.3）。

上传并部署（示例假定已配置 ssh 主机别名 `prod`，占位符见 §0.1）：

```bash
scp "$SERVER_PKG" prod:/tmp/
ssh prod 'sudo mkdir -p /data/apps/zg-homework-server'
ssh prod "sudo tar -xzf $SERVER_PKG -C /data/apps/zg-homework-server --strip-components=1"
ssh prod 'cd /data/apps/zg-homework-server && sudo sh scripts/install.sh \
  --server-dir /data/apps/zg-homework-server \
  --api-port 8000 \
  --database-url "mysql+pymysql://zg_hw_user:密码@127.0.0.1:3306/homework_points?charset=utf8mb4" \

```

服务端归档的顶层目录名固定为 `zg-homework-server/`，因此解压时需要 `--strip-components=1`。

## 五、前端部署

### 5.1 生成共享 nginx 片段（前端 `install.sh`）

**第 0 步：把前端源码（部署脚本）送上生产机。**
片段生成与发布都要靠 `/data/apps/zg-homework-web/scripts/` 下的脚本执行，而**静态包里没有任何脚本**
（只有 `index.html` + `assets/`），本身无法自举——所以第一步必须上传**源码包**：

```bash
# 1) 在开发机打包源码包（含 src/ 与 scripts/install.sh、scripts/web_deploy.sh）
cd <开发机上的 zg-homework-web 检出目录>
sh scripts/web_package.sh --source -o "$WEB_SRC_PKG"
#    产物顶层目录名固定为 zg-homework-web/，解包时要 --strip-components=1

# 2) 上传并解包到生产机（解包得到 scripts/、src/ 等）
scp "$WEB_SRC_PKG" prod:/tmp/
ssh prod 'sudo mkdir -p /data/apps/zg-homework-web'
ssh prod "sudo tar -xzf $WEB_SRC_PKG -C /data/apps/zg-homework-web --strip-components=1"
```

**第 1 步：生成片段。**

```bash
cd /data/apps/zg-homework-web

# 先干跑，看清楚将要写入的片段（不写任何文件、不需要 nginx 可执行）
sh scripts/install.sh --print-only

# 正式安装片段
sudo sh scripts/install.sh \
  --web-prefix /homework/ \
  --api-prefix /homework_api/ \
  --api-upstream 127.0.0.1:8000
```

| 参数 | 默认值 | 说明 |
|---|---|---|
| `--web-prefix` | `/homework/` | 前端路径前缀，必须以 `/` 开头**并以 `/` 结尾** |
| `--api-prefix` | `/homework_api/` | 后端路径前缀，同样首尾带斜杠 |
| `--api-upstream` | `127.0.0.1:8000` | 后端上游，只允许 `127.0.0.1:PORT` |
| `--deploy-dir` | `/var/lib/zg-homework-web` | **只接受该默认值** |
| `--snippet-file` | `/etc/nginx/conf.d/zg-homework.conf` | **只接受该默认值** |
| `--nginx-bin` | `nginx` | nginx 可执行文件；名字走 PATH，含斜杠的按路径判断 |
| `--nginx-main-conf` | `/etc/nginx/nginx.conf` | 主配置路径（仅用于 `nginx -t` 与 include 检查），必须是绝对路径 |
| `--root` | `/` | 根前缀，仅用于沙箱测试，必须是绝对路径 |
| `--no-reload` | 关 | 生成片段后不 reload nginx |
| `--print-only` | 关 | 只打印片段内容，不写任何文件 |

**退出码**：`0` 成功；`2` 参数错误（无法识别的参数、缺少取值）；`1` 校验失败。

行为要点：

- 片段内容**逐字由参数生成**；参数不变时重复执行为 no-op（先比对，相同就跳过写入与 reload）。
- 写入采用「临时文件 + 原子替换」，失败不留半成品；片段内容变化前先备份原文件。
- `nginx -t` **不通过则恢复原片段**（原来没有片段则删掉新片段）并以非零码退出，**绝不 reload**。
- 找不到 nginx 可执行文件时报「找不到 nginx 可执行文件」并**明确提示未写入任何文件**——不会误删已写好的片段。
- 主配置里没有 `include … conf.d` 时会打印告警：片段不会生效（`nginx -t` 照样通过）。
- 建 `/var/lib/zg-homework-web/releases/`（`0755`）。

### 5.2 打包静态产物（`web_package.sh`）

在**开发机或 CI** 上执行（生产机不需要 Node）：

```bash

# 默认输出：<仓库根>/zg-homework-tests/tar/zg-homework-web-static-<时间戳>.tar.gz

# 源码包（含部署脚本，用于把 install.sh / web_deploy.sh 送到生产机）

# 输出：<仓库根>/zg-homework-tests/tar/zg-homework-web-source-<时间戳>.tar.gz
```

静态包构建时已注入 `VITE_API_BASE_URL=/homework_api`，并以 `--base /homework/` 构建，
因此产物里的资源路径与 API 前缀都是生产形态。

静态包的**顶层目录名固定为 `zg-homework-web-static/`**，内容为 `index.html` 与 `assets/`。
`web_deploy.sh` 校验这个顶层目录名、校验 `index.html` 存在，并拒绝符号链接、特殊文件、绝对路径条目与
路径穿越条目。

> **源码包不能直接发布**：它的顶层目录名是 `zg-homework-web/`，`web_deploy.sh --package` 会以
> 「静态包的顶层目录必须是 `zg-homework-web-static/`」拒绝。
>
> 源码包的**主要用途是把部署脚本送到生产机**：静态包里只有 `index.html` + `assets/`、**一个脚本都没有**，
> 本身无法自举，必须先用源码包把 `scripts/install.sh`、`scripts/web_deploy.sh` 落到主机上（§5.1 第 0 步），
> 再用它们发布静态包。

> 「在服务器本机构建」是源码包的**另一种**可选用途，那种场景走 `web_deploy.sh --build`（§5.4）。

打包产物**不含任何凭据**：构建产物里只有静态资源；源码包排除 `.env`、缓存、依赖目录与运行时数据，
但会**逐个固定**地带上 `index.html`、`package.json`、`package-lock.json`、`tsconfig.json`、
`vite.config.ts`、`Dockerfile`、`nginx.conf`、`README.md` 与 `scripts/` 下的四个脚本——
其中 `scripts/install.sh` 与 `scripts/web_deploy.sh` 正是要送上生产机的东西。

### 5.3 发布（`web_deploy.sh --package`，生产机默认模式）

```bash
cd /data/apps/zg-homework-web

sudo sh scripts/web_deploy.sh --package "$WEB_PKG" --source-dir /data/apps/zg-homework-web
```

`--source-dir` 在 `--package` 模式下**只用于记录归属来源**（写进版本目录的 `.web-run-owner`），
不影响发布内容；不给的话归属会记成 `<unknown>`。

生产机只需要 tar 与 nginx，**不需要 Node**。

### 5.4 发布（`web_deploy.sh --build`，服务器本机构建模式）

```bash
cd /data/apps/zg-homework-web
npm ci                      # 需要 node_modules
sudo sh scripts/web_deploy.sh --build
# 指定源码检出目录
sudo sh scripts/web_deploy.sh --build --source-dir /data/apps/zg-homework-web
```

前置条件：`node` ≥ 20、`node_modules/.bin/tsc` 与 `node_modules/.bin/vite` 可执行。
构建等价于 `tsc --noEmit --incremental false` 加
`vite build --mode production --base /homework/ --outDir <版本目录> --emptyOutDir`，
并注入 `VITE_API_BASE_URL=/homework_api`。

`web_deploy.sh` 的参数：

| 参数 | 默认值 | 说明 |
|---|---|---|
| `--package` | 无 | `web_package.sh` 产出的静态包路径（**推荐**，生产机无需 Node） |
| `--build` | 无 | 在服务器本机构建（需要 Node 20+ 与 `node_modules`）；与 `--package` **互斥** |
| `--deploy-dir` | `/var/lib/zg-homework-web` | **只接受该默认值** |
| `--source-dir` | 无 | `--build` 用它构建；`--package` 用它记录归属来源，缺省时归属记为 `<unknown>`；必须是绝对路径 |
| `--nginx-bin` | `nginx` | nginx 可执行文件 |
| `--nginx-main-conf` | `/etc/nginx/nginx.conf` | nginx 主配置路径；必须是绝对路径 |
| `--root` | `/` | 沙箱前缀，仅用于测试 |
| `--no-reload` | 关 | 切换 `current` 后不 reload nginx |

**退出码**：`0` 成功；`2` 参数错误（既没给 `--package` 也没给 `--build`，或两者都给）；`1` 发布失败。

### 5.5 发布流程与语义

1. 前置检查：`<deploy-dir>/releases` 必须存在且不是符号链接（否则提示先跑前端 `install.sh`）；
   `current` 若已存在必须是**受管理的符号链接**（真实目录会被拒绝并要求人工确认）；
   nginx 可执行文件必须存在。
2. **并发锁**：整个发布过程持有发布目录的独占锁（与 `web_run.sh` 同一把锁）。
   并发发布会交错 reload 与历史版本清单，因此第二个发布会被直接拒绝：
   `发布目录已被锁定（另一个发布或服务控制操作正在进行）`。
3. 产出**版本化目录** `releases/web-<UTC 时间戳>-<种子哈希前 8 位>-<随机后缀>/`。
   随机后缀保证同一秒内连续两次发布不会撞名。
4. 写入**归属标记** `.web-run-owner`（内容 = 源码检出目录绝对路径 + 换行）。
   `--package` 模式给了 `--source-dir` 就记录它，没给则写 `<unknown>`；`--build` 模式记录构建所用目录。
   该标记用于让两套前端脚本能区分彼此的 `current`。
5. **`nginx -t` 校验**：不通过则**删除本次版本目录、不切换 `current`、不 reload**，以非零码退出。
6. **原子切换** `current`：在发布目录下建临时符号链接，再用 `os.replace` 覆盖 `current`——绝不先删后建。
7. **reload**：失败则把 `current` 指回上一版本并 reload 恢复；若无上一版本可恢复，会明确提示需人工检查。
8. **旧版本目录不会自动删除**。脚本会打印「保留的历史版本（需人工确认后清理）」列表——
   可能有 worker 正在服务旧目录里的文件，需人工确认后清理。

### 5.6 两种前端部署形态互斥

| 形态 | 脚本 | nginx | 产物目录 | 归属标记 |
|---|---|---|---|---|
| 独占 nginx | `web_run.sh` | 自己的 systemd nginx unit + 专用配置 `/etc/zg-homework-web/nginx.conf` | `WEB_DEPLOY_DIR`（默认 `/var/lib/zg-homework-web`） | 自己的检出目录 |
| 共享 nginx | `web_deploy.sh` | 共享 nginx 的 `conf.d` 片段 | `--deploy-dir`（默认 `/var/lib/zg-homework-web`） | `--source-dir`，缺省 `<unknown>` |

**两者的默认值相同（都是 `/var/lib/zg-homework-web`），因此冲突是默认可达的。**
`web_run.sh` 的使用者必须把 `WEB_DEPLOY_DIR` 指向别处：

```bash
WEB_DEPLOY_DIR=/var/lib/zg-homework-web-exclusive \
WEB_NGINX_CONFIG=/etc/zg-homework-web/nginx.conf \
WEB_PORT=8080 \
  sh /data/apps/zg-homework-web/scripts/web_run.sh status
```

归属标记的值与 `web_run.sh` 的检出目录**不同**即互斥：`web_run.sh` 的 `current_target()` 要求标记逐字等于
它自己的检出目录，因此它会拒绝接管 `web_deploy.sh` 发布的版本。
（例外：标记值**相同**时并不互斥——`--build` 模式缺省的 `--source-dir` 就是模块目录。
结论不变：**两种形态不应混用同一个发布目录**。混用同一目录前须先手工清理 `current` 与 `releases/`。）

本方案使用的是**共享 nginx** 形态（`web_deploy.sh`）。

## 六、共享 nginx 片段规范

### 6.1 片段全文

`/etc/nginx/conf.d/zg-homework.conf`（由前端 `install.sh` 生成，**请勿手工编辑**）：

```nginx
# 由 zg-homework-web/scripts/install.sh 生成，请勿手工编辑。
# 同域名多项目共存：本项目独占 /homework/ 与 /homework_api/ 两个前缀。
# 本片段只含 location 块；server 块与 TLS 证书由运维统一维护。

location /homework/ {
    alias /var/lib/zg-homework-web/current/;
    index index.html;
    try_files $uri $uri/ /homework/index.html;
}

location /homework_api/ {
    proxy_pass http://127.0.0.1:8000;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Real-IP $remote_addr;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header X-Forwarded-Proto $scheme;
    client_max_body_size 12m;
    proxy_read_timeout 60s;
}
```

两个必须记牢的细节：

- **`proxy_pass` 不带末尾 `/`**。服务端路由本身带 `/homework_api` 前缀（`app/main.py:45`），
  nginx 若带上末尾斜杠就会把前缀剥掉，后端收到的是 `/login` 而不是 `/homework_api/login` → **404**。
- **`alias` 必须带末尾 `/`**。否则 nginx 拼接路径会出错 → **403/404**。

其它要点：

- `try_files` 的回退值 `/homework/index.html` 是 **URI** 而非文件路径，nginx 会重新匹配
  `location /homework/`，再由 `alias` 解析为 `current/index.html`。少了前缀就会变成深链刷新 404。
- `client_max_body_size 12m` 是作业文件上传的上限，需与后端 `MAX_UPLOAD_MB` / `ARTICLE_MAX_UPLOAD_MB`
  配合；后端限额更小时以后端为准。
- 片段里**没有** `server` 块，也**没有** `listen`——监听与 TLS 由运维的 server 块负责。

### 6.2 主配置的 `include` 约定（运维负责）

运维在共享 nginx 的 server 块内 include 本目录：

```nginx
server {
    listen 80;
    listen 443 ssl;
    server_name xxx.com;

    # 证书路径由运维维护
    ssl_certificate     /etc/nginx/tls/xxx.com/fullchain.pem;
    ssl_certificate_key /etc/nginx/tls/xxx.com/privkey.pem;

    # 本项目的片段
    include /etc/nginx/conf.d/*.conf;

    # 其它项目的片段同理，各自一个文件
}
```

**主配置必须 include `conf.d` 目录**，否则 `nginx -t` 照样通过，但本项目片段根本不会生效。
前端 `install.sh` 会检查主配置里是否含 `include … conf.d`，未找到时打印明确告警。

主配置、server 块与站点配置目录由运维统一维护，**本项目的任何脚本都不写这些位置**。

### 6.3 reload 纪律

- 本项目**只在自己的片段变化后**才 reload；片段内容未变时前端 `install.sh` 直接跳过写入与 reload。
- reload 前必定先 `nginx -t`：不通过就不切换、不 reload（`install.sh` 恢复原片段，`web_deploy.sh` 不切换 `current`）。
- `nginx -s reload` 是平滑的，不打断其它项目的在途请求。
- 手工改片段后，务必自己执行 `nginx -t && systemctl reload nginx`。

## 七、数据库初始化

### 7.1 初始化命令

应用配置只从**环境变量**与检出目录下的 `.env` 读取（`zg-homework-server/app/config.py`）。
systemd 的 `EnvironmentFile` 只对服务进程生效，手工执行初始化/迁移脚本时必须自己把生产配置导入环境：

```bash
sudo -u www-data bash -c '
  set -a; . /etc/zg-homework-server/env; set +a
  cd /data/apps/zg-homework-server && PYTHONDONTWRITEBYTECODE=1 ./.venv/bin/python -m app.seed.initial_data
'
```

> **为什么必须带 `PYTHONDONTWRITEBYTECODE=1`（或 `python -B`）**
>
> `server_run.sh` 的契约校验会遍历检出目录的 `app/`，一旦发现 `*.pyc` / `*.pyo` 就**直接拒绝**控制该单元，
> 报「app 中存在字节码；请在启动前由运维人员检查并清除」。
> systemd 单元里已经设了 `Environment=PYTHONDONTWRITEBYTECODE=1`，所以**只有这些手工执行的
> 初始化 / 迁移 / 重置密码命令**会在检出目录里留下 `app/**/__pycache__/*.pyc`，
> 紧接着的 `server_run.sh check` / `restart` 就会失败。
>
> 已经污染过的检出目录这样清理（会删掉 `app/` 下全部 `__pycache__`，不影响源码）：
>
> ```bash
> find /data/apps/zg-homework-server/app -name '__pycache__' -prune -exec rm -rf {} +
> ```

> `env` 文件的取值不含引号、反斜杠、`$` 与首尾空白（`server_run.sh` 的硬约束），
> 因此可以被 shell 正常 `source`，不需要额外的转义处理。

`install.sh` **不**执行数据库初始化，这一步必须手工做。

- 幂等：重复执行不重复插入。
- 建表用 SQLAlchemy `create_all()`，只建**缺失的表**。
- 创建 `admin` 账号：若 `admin` 已存在则原样跳过，**不覆盖已有 admin 密码**。
  `ADMIN_INIT_PASSWORD` 为空时随机生成密码并**只打印一次**到日志，请立即登录修改。
- 想指定初始密码，先在 `/etc/zg-homework-server/env` 里设置 `ADMIN_INIT_PASSWORD=你的初始密码`，
  再执行上面那条初始化命令。

忘记密码时用重置命令（同样需要导入生产配置，同样要带 `PYTHONDONTWRITEBYTECODE=1`）：

```bash
sudo -u www-data bash -c '
  set -a; . /etc/zg-homework-server/env; set +a
  cd /data/apps/zg-homework-server && PYTHONDONTWRITEBYTECODE=1 ./.venv/bin/python -m app.utils.reset_password admin --password "admin123456"
'
# 省略 --password 则随机生成并打印
```

### 7.2 `create_all()` 不加列——必须跑迁移脚本

仓库**没有** Alembic。`Base.metadata.create_all()` **只建缺失的表，不修改已有表的结构**——
给已存在的表新增字段必须显式 `ALTER`。涉及表结构变化的版本，部署前必须执行对应的迁移脚本：

| 迁移脚本 | 作用 |
|---|---|
| `app/seed/migrate_v21.py` | 为 `articles` 表增加 `file_url` / `file_name` / `file_type`（幂等） |
| `app/seed/migrate_homework_review.py` | 作业批改：新增批改字段 + 建档位表 + 写档位种子 |
| `app/seed/migrate_article_soft_delete.py` | 为 `articles` 表增加软删除列 |

```bash
for m in migrate_v21 migrate_homework_review migrate_article_soft_delete; do
  sudo -u www-data bash -c "
    set -a; . /etc/zg-homework-server/env; set +a
    cd /data/apps/zg-homework-server && PYTHONDONTWRITEBYTECODE=1 ./.venv/bin/python -m app.seed.$m
  "
done
```

**迁移前必须备份数据库**（见 §9.3）。MySQL 的 DDL 会隐式提交，事务回滚保护不了 DDL；
`migrate_homework_review.py` 在「首次建表后、种子提交前中断」的情况下会检测到空表并停止，
不会猜测或覆盖管理员的配置——此时须人工按报错与 PRD 恢复。迁移脚本**串行执行**，不要并发。

- 同域名下所有项目**共用一张证书**，由运维统一申请、续期与部署。

  ```bash
  echo | openssl s_client -connect xxx.com:443 -servername xxx.com 2>/dev/null \
    | openssl x509 -noout -dates -subject
  ```

## 九、升级、回滚与备份

### 9.1 服务端升级流程

```bash
TS=$(date +%Y%m%d-%H%M%S)

# 0) 备份数据库、数据目录与生产配置（完整清单见 §9.3）
sudo mkdir -p /backup
#    注意：/backup 是 root 属主，重定向由当前用户执行会 Permission denied，
#    所以 mysqldump 与 tee 都要 sudo（管道两端都要）。
sudo mysqldump -h 127.0.0.1 -u zg_hw_user -p --single-transaction --routines --triggers homework_points \
  | sudo tee /backup/homework_points-$(date +%Y%m%d).sql > /dev/null
sudo tar -czf /backup/zg-homework-data-$(date +%Y%m%d).tar.gz -C /var/lib zg-homework/
sudo cp /etc/zg-homework-server/env /backup/env-$(date +%Y%m%d)

# 0.1) 备份旧代码目录 —— 必须在覆盖之前做，否则备份里装的是新代码
#      cp -a 会把 .venv 一并复制过去（体积大、venv 里的脚本带绝对路径）；
#      回滚时若不需要旧 venv，可删掉备份里的 .venv。
sudo cp -a /data/apps/zg-homework-server /data/apps/zg-homework-server.bak-$TS

# 1) 停服
cd /data/apps/zg-homework-server
sudo sh scripts/server_run.sh stop

# 2) 覆盖代码（保留 .venv 与 env；归档顶层是 zg-homework-server/，故 --strip-components=1）
sudo tar -xzf "$SERVER_PKG" -C /data/apps/zg-homework-server --strip-components=1

# 3) 仅在 requirements.txt 发生变化时重建虚拟环境
#    （init_check.sh 拒绝覆盖已有的 .venv，必须先删；依赖没变就跳过这两行）
#    INIT_PYTHON 必须指向 3.12+ 的解释器，与 §4.4 一致
#    sudo rm -rf /data/apps/zg-homework-server/.venv
#    cd /data/apps/zg-homework-server && sudo INIT_PYTHON=python3.12 sh scripts/init_check.sh

# 4) 表结构有变化时跑迁移脚本（§7.2）

# 5) 重新安装（保留已有 env 与 JWT_SECRET，不带 --force-env）
sudo sh scripts/install.sh \
  --server-dir /data/apps/zg-homework-server \
  --api-port 8000 \
  --database-url 'mysql+pymysql://zg_hw_user:密码@127.0.0.1:3306/homework_points?charset=utf8mb4' \
  --data-dir /var/lib/zg-homework

# 6) 重启并验证
sudo sh scripts/server_run.sh restart
sudo sh scripts/server_run.sh check
```

第 5 步**不要**加 `--force-env`：那会重新生成 `JWT_SECRET`，导致所有已签发的 token 立即失效。
`install.sh` 重复执行是幂等的——已有 `.venv` 复用、已有 env 的键值保留、已有数据目录不重建。

> 第 2 步是**就地解压**，旧版本中已被删除的文件会残留在检出目录里。
> 若要彻底清理，把旧目录整体移走再解压新的：
> `sudo mv /data/apps/zg-homework-server /data/apps/zg-homework-server.old && sudo mkdir -p /data/apps/zg-homework-server && sudo tar -xzf … -C /data/apps/zg-homework-server --strip-components=1`
> （注意：systemd 单元的 `WorkingDirectory` 必须仍是 `/data/apps/zg-homework-server`，路径不能改。）
>
> 用 `mv` 的方式同时也是**回滚路径**：旧目录原封不动留在 `.old` 里，出问题时
> `sudo rm -rf /data/apps/zg-homework-server && sudo mv /data/apps/zg-homework-server.old /data/apps/zg-homework-server`
> 即可换回旧代码（`.venv` 也一并回来了）。

### 9.2 前端升级与回滚

升级即发布新版本：

```bash
scp "$WEB_PKG" prod:/tmp/
ssh prod "cd /data/apps/zg-homework-web && sudo sh scripts/web_deploy.sh --package $WEB_PKG --source-dir /data/apps/zg-homework-web"
```

**自动回滚**：`web_deploy.sh` 在切换 `current` 之后 reload 失败时，会把 `current` 指回上一版本并 reload 恢复；
`nginx -t` 不通过则根本不切换。两种情况都不需要人工干预。

**手工回滚**（推荐——走同一条校验过的发布路径）：

```bash
# 上一版的静态包，按实际文件名替换（时间戳格式同 §0.2）
WEB_PKG_PREV=/tmp/zg-homework-web-static-20261113-090000.tar.gz

cd /data/apps/zg-homework-web
sudo sh scripts/web_deploy.sh --package "$WEB_PKG_PREV" --source-dir /data/apps/zg-homework-web
```

**手工回滚**（旧包已不在时的兜底）：

```bash
cd /var/lib/zg-homework-web
ls -1 releases                       # 找到要回退到的版本目录
sudo ln -sfn releases/web-20261113-090000-a1b2c3d4-9f8e current
sudo nginx -t && sudo systemctl reload nginx
```

注意：手工 `ln -sfn` **不是原子操作**（`web_deploy.sh` 用临时链接 + `os.replace` 才是），
所以优先用「重新发布旧包」的方式回滚。

另外要说清楚 `web_deploy.sh` 的「受管理版本」判定：它看的是**符号链接解析后的目标**——
目标必须直接位于 `releases/` 之下且是真实目录。因此上面那条
`ln -sfn releases/web-… current` 造出来的链接**恰恰是受管理的**，
`web_deploy.sh` 会把它当作合法的上一版本，在下次 reload 失败时写回去。
只有指向 `releases/` **之外**（例如 `/etc/…`）的符号链接才算「不受管理」，
那时它不会拿它回滚，而会明确提示「不作为回滚目标……请人工检查」。

### 9.3 备份项清单

| 备份对象 | 命令 | 说明 |
|---|---|---|
| 数据库 | `sudo mysqldump -h 127.0.0.1 -u zg_hw_user -p --single-transaction --routines --triggers homework_points \| sudo tee /backup/homework_points-$(date +%Y%m%d).sql > /dev/null` | **迁移前必做**。`/backup` 是 root 属主，管道两端都要 sudo，否则重定向/写入 Permission denied |

| 服务端代码 | `server_package.sh` 产物 + 版本号 | 按版本归档 |

备份目录 `/backup` 需事先建好并按机密文件管理（`sudo mkdir -p /backup`，root 属主）。

### 11.2 端口与 worker 数是硬约束

- **端口 8000**：`server_run.sh` 的 `SERVER_PORT` 默认 8000，`production.env.example` 与单元模板一致。
  `install.sh --api-port` 改了端口后，`server_run.sh` 必须带 `SERVER_PORT=<port>`，否则会拒绝这个单元。
- **单 worker**：`ExecStart` 里的 `--workers 1` 是硬要求。成语接龙的会话状态保存在**进程内存**里
  （`app/routers/games.py` 的会话存储），多 worker 会话会被分发到另一个进程而丢失。
  `server_run.sh` 会逐字校验 `ExecStart`，`--workers` 不是 1 直接拒绝控制该单元。

### 11.3 故障对照表

| 现象 | 原因 | 处置 |
|---|---|---|
| `/homework/` 返回 403 或 404 | `alias` 末尾缺 `/`；`current` 悬空（指向已删目录）；`releases/` 权限不对 | 核对片段里 `alias ... /current/;` 末尾斜杠；`readlink -f /var/lib/zg-homework-web/current` 看是否有效 |
| 刷新深链 404 | `try_files` 回退值没带 `/homework/` 前缀 | 回退值必须是 URI `/homework/index.html`，不是文件路径 |
| 接口 404 | `proxy_pass` 多了末尾 `/`，`/homework_api` 前缀被剥掉 | 去掉 `proxy_pass` 的末尾斜杠；服务端路由自带 `/homework_api` 前缀 |
| 接口 502 | 后端未启动；上游端口不是 8000；单元启动失败 | `sudo systemctl status zg-homework-server`；`journalctl -u zg-homework-server -n 100 --no-pager`；`ss -ltnp \| grep ':8000'` |
| 页面白屏、资源 404 | 前端产物不是按 `base=/homework/` 构建；Router basename 缺失 | 重新用 `web_package.sh` / `web_deploy.sh --build` 打包发布（构建已固定 `--base /homework/`） |
| 片段不生效（前端全 404） | 主配置的 server 块没 `include /etc/nginx/conf.d/*.conf;` | 运维在主配置里补上 include；`nginx -t` 通过不代表片段被加载 |
| `server_run.sh check` 报「生产配置文件格式不受支持」 | env 里含 `'"\$`、控制字符、首尾空白、重复键、未替换的 `__…__` 占位符，或键名不在允许集合内 | 按 §4.3 的硬约束逐项修正 `/etc/zg-homework-server/env` |
| 上传文件丢失 | `UPLOAD_DIR` / `PRIVATE_HOMEWORK_DIR` 落在代码目录内（被升级覆盖），或两者互相重叠 | 把两个目录移到 `/var/lib/zg-homework/` 下并重启服务 |
| 成语接龙会话丢失 | worker 数大于 1 | 单元 `ExecStart` 必须是 `--workers 1`；改完 `systemctl daemon-reload` 并重启 |
| 前端发布报「发布目录已被锁定」 | 另一个发布或 `web_run.sh` 控制操作正在进行 | 稍后重试；确认没有并行的发布进程 |
| 前端发布报「已存在但不是受管理的符号链接」 | `current` 被手工改成了真实目录 | 人工确认后删掉 `current`，再重新发布 |
| 服务端 install 报「`--data-dir` 不得等于或位于服务端检出目录的上级目录之下」 | 数据目录落在检出目录的父目录（`/data/apps`）之下 | 把数据目录改到 `/var/lib/zg-homework/` |
| 服务端 install 报「`--env-file` 只能是 /etc/zg-homework-server/env」 | 试图改生产配置路径 | 用默认值；配置路径是写死的硬约定 |

## 十二、脚本职责对照表

| 脚本 | 职责 | 可重复执行 | 写入范围 |
|---|---|---|---|
| `zg-homework-server/scripts/install.sh` | 渲染 systemd 单元、生成生产配置、建数据目录、建/复用 venv、启动服务 | 是（已有 venv 复用、已有 env 保留、已有数据目录不重建） | `/etc/systemd/system/zg-homework-server.service`、`/etc/zg-homework-server/env`、`/var/lib/zg-homework/**`、检出目录内的 `.venv` |
| `zg-homework-server/scripts/server_run.sh` | 单元控制器：`check` / `status` / `start` / `stop` / `restart` | 是（`start` 幂等；服务已运行且健康时不执行任何操作） | 不写任何文件（只调用 `systemctl`） |
| `zg-homework-server/scripts/server_package.sh` | 把服务端工作树打包成部署归档（`app/` 目录树 + 白名单固定文件：`requirements.txt`、`.env.example`、`Dockerfile`、`.dockerignore`、`README.md`、`scripts/*`） | 是（输出文件必须是不存在的新文件名） | 只写指定的 `.tar.gz` 输出文件 |
| `zg-homework-server/scripts/init_check.sh` | 创建 `.venv` 并安装依赖 | 否（**拒绝覆盖**已有 `.venv`；重建须先自行删除） | 检出目录内的 `.venv` |
| `zg-homework-web/scripts/install.sh` | 生成共享 nginx 片段、建 `releases/`、校验并 reload | 是（片段内容未变则跳过写入与 reload） | `/etc/nginx/conf.d/zg-homework.conf`（**只写自己这一个片段**）、`/var/lib/zg-homework-web/releases/` |
| `zg-homework-web/scripts/web_deploy.sh` | 发布前端：解包静态包或本机构建 → 版本目录 → `nginx -t` → 原子切 `current` → reload；失败自动回滚 | 是（每次发布新增一个版本目录，不覆盖旧的） | `/var/lib/zg-homework-web/**`（**不写 `/etc/nginx/` 下任何文件**） |
| `zg-homework-web/scripts/web_package.sh` | 构建并打包静态部署包（`--source` 打包源码：含 `src/` 与 `scripts/`，用于把部署脚本送上生产机） | 是（输出文件必须是不存在的新文件名） | 只写指定的 `.tar.gz` 输出文件 |
| `zg-homework-web/scripts/web_run.sh` | **独占 nginx 形态**的前端控制器（本方案不使用；使用者必须把 `WEB_DEPLOY_DIR` 指到别处） | 是（`start` 幂等；`restart` 会构建新版本） | 构建产物写入 `WEB_DEPLOY_DIR` 指向的目录；unit 与专用 nginx 配置只校验不写 |
